# 播放队列由引擎持有

现在「下一首是谁」由 UI 决定：UI 观察到 `finished_serial` 变化后自己调 `load`
（`player_view.rs:361-364`），而 `Load` 会先清空缓冲（`engine.rs:185`）。这意味着
缓冲必然在两首之间被抽干一次 —— 只要引擎在上一曲播完前不知道下一首，gapless
原理上就做不到。所以队列下移到引擎。

引擎持有「曲目序列 + 游标 + 循环模式 + 随机序列」，对外暴露
`SetQueue / Next / Prev / SetMode` 一类接口；UI 不再计算下一首，只负责编辑列表
并把新队列推回引擎。

## 考虑过的选项

**UI 在 `load` 时把下一首路径一起告诉引擎（只做预读）**：改动小得多，但随机与
循环的交互就留在 UI 侧，等于「预读时已经决定好的下一首」和「用户看到的列表」是
两个真相，且进一步违反「UI 只通过 `Player` 公开接口操作播放」。

## 后果

- 「接下来播什么」只剩一个权威来源；列表的增删仍属 UI，改完整条推回引擎。
- 随机是**预先算好的打乱序列**，所以「上一首」有明确定义；切换随机模式要重算序列
  并保留已播部分的历史。
- 会话恢复需要的「当前队列 + 游标」天然存在，UI 不必另存一份。
- 引擎 crate 依然不依赖 GPUI：队列里只放路径与曲目标识，不放任何界面类型。
- gapless 只是这条决定的一个结果，不是它的目的；将来做交叉淡化、按队列统计播放次数
  都落在同一处。
